# ADR-002 – Adoção de Composite Actions e Estratégias de Promoção Definitivas

**Status:** Aceito
**Data:** 2026-10-02
**Projeto:** reusable-actions
**Decisores:** Maintainers do projeto

---

## Contexto

Na evolução do projeto `reusable-actions`, identificamos que manter o fluxo inteiro amarrado puramente a *Reusable Workflows* (`workflow_call`) limitava o controle do consumidor. Consumidores muitas vezes queriam apenas detectar a stack ou rodar a cobertura para usar em seus próprios steps customizados, mas a granularidade do projeto não permitia isso.

Adicionalmente, as estratégias de promoção de branch estavam com nomes ambíguos (`direct`, `always-to-main`, etc.) e o fluxo de PRs gerava confusão em repositórios grandes que exigem fluxos mais robustos como o Gitflow clássico.

Era necessário refatorar a arquitetura base para permitir adoção em "níveis" (do atômico ao fluxo completo) e oficializar nomenclaturas de mercado para os fluxos de branch.

---

## Decisão

### 1. Arquitetura em Duas Camadas (Composite Actions + Reusable Workflows)

Decidimos componentizar a lógica interna do projeto.
Em vez de ter steps enormes dentro do `ci-quality-gate.yml`, a lógica atômica foi movida para **Composite Actions** no diretório `/actions/`.

Foram criadas:
- `actions/detect-stack`: resolve se o projeto é Node, PHP, etc.
- `actions/setup-runtime`: instala dependências (ex: setup-node)
- `actions/run-tests`: executa testes abstratos
- `actions/run-coverage`: executa a cobertura e normaliza para o contrato `.normalized.json`
- `actions/semantic-release`: empacota o semantic-release e o strict mode
- `actions/create-pr`: abstrai a criação/update de PR com labels.

**Racional:**
* Consumidores podem usar o framework de modo "Quick" (`uses: .../.github/workflows/ci.yml`) ou de modo "Custom" montando seu próprio fluxo (`uses: .../actions/detect-stack`).
* Reduz os 4 checkouts que ocorriam antes no workflow principal para apenas 1, já que os scripts e a lógica ficam dentro da mesma *action_path*.

### 2. Três Estratégias de Promoção (Naming Definitivo)

As estratégias de branch suportadas oficialmente pela *Engine de Promoção* do `cd-pull-request` passam a se chamar:

| Estratégia  | Descrição do Fluxo |
|-------------|--------------------|
| **`trunk`** | Promoção direta: `feature/**` → PR para `main`. |
| **`develop`** | Fluxo intermediário: `feature/**` → PR para `develop`. Ao mergir na develop, semantic-release roda e, **se houver nova versão detectada**, abre PR para `main`. |
| **`gitflow`** | Fluxo release branch: `feature/**` → PR para `develop`. Ao mergir na develop, **se houver versão**, abre PR para `release-x.y.z`. Ao finalizar QA, a `release-x.y.z` abre PR para `main`. |

**Racional:**
Nomes como `trunk`, `develop` e `gitflow` são amplamente compreendidos na indústria. Eles substituem `direct` e `to-release` que eram ambíguos.

### 3. Hotfix Override

Branches prefixadas com `hotfix/*` continuam servindo como mecanismo de *override* de emergência. Não importa a estratégia configurada, push num hotfix abre um PR diretamente para a `main`, contornando `develop` e ignorando a checagem de nova versão.

---

## Consequências

### Positivas
* Reuso maximizado: consumidores podem "pinçar" apenas as features que desejam (ex: apenas a normalização de cobertura).
* Manutenção mais fácil: lógica do shell script separada e empacotada por contexto.
* Menor tempo de execução (redução de overhead de checkout).
* Entendimento imediato das estratégias de fluxo para novos integrantes das equipes consumidoras.

### Negativas / Trade-offs
* O repositório consumidor deve informar corretamente o `project_path` caso seu projeto não esteja na raiz do repositório de checkout, já que a *action* isolada não faz navegação recursiva por padrão.

---

## Status final

Esta decisão está **ativa** e baseia a estrutura de repositório `v1` do framework.
