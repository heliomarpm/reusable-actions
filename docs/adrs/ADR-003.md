# ADR-003 – Action Nativa de Changelog Agnóstica com Ciclo de Vida [Unreleased] e Promoção por Data/SemVer

**Status:** Aceito  
**Data:** 2026-10-03  
**Projeto:** reusable-workflows  
**Decisores:** Maintainers do projeto  

---

## Contexto

Embora o ecossistema `semantic-release` fornecido por este framework atenda com excelência projetos de software com pipelines completos de compilação e publicação de pacotes, identificamos cenários onde essa abordagem se torna desnecessariamente onerosa:

1. **Repositórios sem stack tradicional:** Repositórios de documentação, infraestrutura/Terraform, configurações, templates e o próprio repositório de ações reutilizáveis (`reusable-workflows`) não possuem um ecossistema de aplicação compilada nem dependências em Node.js ou PHP.
2. **Dependência pesada do Semantic-Release:** Para atualizar apenas um arquivo `CHANGELOG.md`, exigir a instalação do Node.js, `npx`, pacotes `@semantic-release/*` e seus plugins adiciona tempo de pipeline e potenciais pontos de falha de rede/npm.
3. **Necessidade de visualização incremental em desenvolvimento:** Equipes que utilizam fluxos com branch `develop` necessitam acompanhar o acúmulo de entregas em uma seção clara `## [Unreleased]`. Ao mesmo tempo, essa seção deve ser única e ser promovida para uma versão oficial quando o código chegar à `main`/`master`.
4. **Versionamento flexível (Data vs SemVer):** Repositórios que não utilizam GitHub Releases ou tags semânticas precisam de um versionamento baseado em data (`YYYY-MM-DD`), enquanto repositórios com tags demandam incremento semântico automático (Major/Minor/Patch).

---

## Decisão

Criar a Composite Action `actions/changelog` acompanhada de engine nativa em Bash puro (`scripts/shared/changelog/run.sh`), com as seguintes diretrizes:

### 1. Zero Dependências Externas
A extração e geração são realizadas exclusivamente via `git log`, `bash`, `awk`, `sed` e `grep`, eliminando a necessidade de Node.js, npm, Python ou qualquer runtime externo. A execução é praticamente instantânea (< 1 segundo).

### 2. Ciclo de Vida da Seção `[Unreleased]`
- **Em branches de desenvolvimento (`develop`, `dev`):**
  - A seção `## [Unreleased]` é gerada ou atualizada no topo do histórico do `CHANGELOG.md`.
  - **Garantia de Seção Única:** Se já existir uma seção `## [Unreleased]`, ela é substituída atomicamente pelo conjunto consolidado de commits desde a última versão lançada, evitando duplicações.
- **Em branches de lançamento (`main`, `master`):**
  - A seção `## [Unreleased]` existente é automaticamente convertida no cabeçalho da nova versão.
  - Não resta seção `[Unreleased]` vazia após a publicação na branch de produção.

### 3. Regra de Resolução de Versão e Template de Formato (`version-format`)
- **Template Flexível por Tokens (`version-format`):** Permite construir qualquer formato combinando tokens semânticos e temporais:
  - SemVer: `%major`, `%minor`, `%patch`
  - Temporais: `%YYYY` (ano 4 dígitos), `%YY` (ano 2 dígitos), `%mm` (mês 2 dígitos), `%m` (mês 1 dígito), `%dd` (dia 2 dígitos), `%d` (dia 1 dígito)
- **Valores Padrão do Template:**
  - Se `create-release: true` (ou tags existentes): assume `"v%major.%minor.%patch"`.
  - Se `create-release: false`: assume `"%YYYY-%mm-%dd"`.
  - Formatos híbridos customizados são suportados nativamente (ex: `"%YYYY.%mm.%patch"`, `"v%YYYY.%mm.%dd"`, `"%major.%minor.%patch"`).
- **Consolidação de Tags e Releases (`create-release`):**
  - Como uma GitHub Release depende inerentemente de uma Git Tag, consolidamos tudo em um único parâmetro booleano: `create-release`.
  - Quando `create-release: true`: cria e envia a Git Tag correspondente e publica a GitHub Release com as notas do changelog.
  - Quando `create-release: false`: apenas atualiza o `CHANGELOG.md` sem criar tags ou releases remotas.
- **Persistência Padrão (`enable-changelog`):**
  - Habilitado por padrão (`true`), garantindo que o arquivo atualizado seja versionado automaticamente na branch corrente via commit `chore(changelog): ...` ou `chore(release): ...`.

### 4. Classificação Padronizada de Conventional Commits
Os commits são agrupados em seções legíveis com emojis:
- ⚠️ **Breaking Changes** (`feat!:`, `fix!:`, `BREAKING CHANGE:`)
- 🚀 **Features** (`feat`)
- 🐛 **Bug Fixes** (`fix`)
- ⚡ **Performance Improvements** (`perf`)
- ♻️ **Code Refactoring** (`refactor`)
- 📝 **Documentation** (`docs`)
- 🧪 **Tests** (`test`)
- 🔧 **CI & Build System** (`ci`, `build`)
- 📦 **Miscellaneous** (`chore`)
- ⏪ **Reverts** (`revert`)
- 🔄 **Other Changes** (commits fora do padrão)

Commits de merge (`Merge pull request...`), releases automáticas (`chore(release)...`) e marcados com `[skip ci]` são automaticamente filtrados para não poluir o changelog.

---

## Consequências

### Positivas
- **Adoção Universal:** Qualquer repositório Git pode utilizar a action sem pré-requisitos de runtime.
- **Dogfooding:** O próprio repositório `reusable-workflows` passa a poder versionar seu `CHANGELOG.md` e gerar tags/releases nativamente.
- **Eficiência Extrema:** Execução em milissegundos sem download de pacotes terceiros.
- **Previsibilidade:** Manutenção estrita de uma única seção `[Unreleased]` durante todo o ciclo de PRs e desenvolvimento.

### Negativas / Trade-offs
- A formatação avançada de notas é limitada aos recursos do parser nativo em Bash, diferentemente de plugins customizados em JavaScript do semantic-release (que continuam disponíveis na action `actions/semantic-release` para projetos que necessitam dessa sofisticação).

---

## Status Final

Esta decisão está **ativa** e implementada a partir da action `actions/changelog`.
